# Технический долг и план по стабильности/безопасности

Документ собран по итогам первого реального деплоя (ветка `chore/server-recon-extra`,
сервер `task.uxteam.space`) — все пункты основаны на конкретных инцидентах и находках
этой сессии, а не на общих best practices. У каждого пункта — что произошло/почему это
важно и что сделать.

Статус на момент написания: сервис задеплоен, админка и кандидатский флоу (`/t/<token>`)
рабочие, тесты (`npm test`) зелёные, `tsc --noEmit` чистый.

## 🔴 Критично — сделать до реального потока кандидатов

### 0. ✅ `DATABASE_URL` указывал мимо смонтированного volume — БД не персистилась — исправлено

**Что произошло:** при код-ревью Волны 2 (проверка п.6, бэкап SQLite) агент эмпирически
воспроизвёл поведение `@prisma/adapter-better-sqlite3` — тот просто отрезает префикс
`file:` (`url.replace(/^file:/, "")`) и передаёт остаток в `better-sqlite3` как есть,
т.е. путь резолвится относительно `process.cwd()` (в контейнере — `/app`), а НЕ
относительно `schema.prisma`, как можно было бы ожидать по привычному поведению Prisma.
В `deploy.yml` было `DATABASE_URL="file:./data/dev.db"` → реальный файл создавался по
`/app/data/dev.db`, а volume `testtask-db` смонтирован на `/app/prisma/data`. Это два
разных, никак не пересекающихся пути. Подтверждено локальным воспроизведением
(`npx prisma migrate deploy` из корня репо с этим `DATABASE_URL` реально создаёт файл
в `data/dev.db`, а не в `prisma/data/dev.db`). Само README (до правки) уже противоречило
себе: в одном месте утверждало, что данные лежат в `prisma/data/dev.db`, а в примере
`docker run` тремя строками ниже стояло `file:./data/dev.db`.

**Риск:** volume физически не покрывал файл БД. Каждый передеплой пересоздавал контейнер
→ `/app/data` (не volume, живёт только в слое контейнера) уничтожался вместе со старым
контейнером → `prisma migrate deploy` при следующем старте создавал **новую пустую БД**
по тому же ошибочному пути. То есть каждый реальный передеплой молча стирал все данные
кандидатов — без единой ошибки в логах и с зелёным health-check (curl `/admin` не
проверяет содержимое БД). Это подрывает и п.6 (бэкап): `backup-db.sh` бэкапил бы
несуществующий/пустой файл в volume.

**Что сделано:** `DATABASE_URL` в `deploy.yml` и `README.md` изменён на
`file:./prisma/data/dev.db` — резолвится в `/app/prisma/data/dev.db`, что совпадает
с точкой монтирования `-v testtask-db:/app/prisma/data`. Добавлен явный комментарий в
README про то, почему путь резолвится через `process.cwd()`, а не через `schema.prisma`.
`.gitignore`/`.dockerignore` дополнены `/prisma/data/` для локальной разработки.

**Обнаружено на живом сервере (2026-07-16):** текущий рабочий контейнер оказался поднят
ещё на дореволюционной схеме — volume смонтирован на весь `/app/prisma` (а не на
`/app/prisma/data`, как в уже смердженном фиксе `ba26d0d`), а `DATABASE_URL` указывал на
`file:./dev.db` → реальный файл БД (53KB на момент проверки) лежал в writable-слое
контейнера, вообще вне volume. Директории `/app/prisma/data` внутри volume не
существовало. Решение: копившиеся на этом контейнере тестовые записи (несколько
demo-submissions, не реальные ответы кандидатов) сознательно **не переносим** —
принята потеря этих данных ради чистого старта на исправленной схеме.

**Обязательная проверка после следующего реального деплоя** (per заметку в конце этого
документа про инфраструктурные регрессии, которые не ловятся тестами) — только зелёные
тесты и health-check это не поймают:
1. Убедиться, что новый контейнер поднялся с `-v testtask-db:/app/prisma/data` и
   `DATABASE_URL=file:./prisma/data/dev.db` (`docker inspect testtask-collector --format
   '{{json .Mounts}}'` + `docker exec testtask-collector env | grep DATABASE_URL`).
2. Создать один тестовый submission через админку, проверить что файл БД появился внутри
   volume: `docker exec testtask-collector ls -la /app/prisma/data/dev.db`.
3. Сделать `docker stop testtask-collector && docker rm testtask-collector`, затем поднять
   контейнер заново той же командой из `deploy.yml` (или просто повторно триггернуть
   деплой) — и убедиться, что тестовый submission из шага 2 **пережил** пересоздание
   контейнера. Это единственный способ реально подтвердить, что volume теперь держит
   данные, а не просто «выглядит смонтированным».

### 1. ✅ `testtask-uploads` volume перекрывает `public/uploads/seed/` так же, как раньше `prisma/` — исправлено

**Что произошло:** volume `testtask-db:/app/prisma` при первом деплое «заморозил» в себе
содержимое `prisma/` (включая `migrations/`) на момент первого запуска. Все последующие
образы с новыми файлами миграций эти файлы просто не видели — `prisma migrate deploy`
молча не находил новых миграций, схема БД разъехалась с кодом
(`P2022: The column main.Submission.openedAt does not exist`). Пофикшено в этой сессии:
volume теперь смонтирован только на `/app/prisma/data`, `migrations/` всегда берётся из
образа (см. `.github/workflows/deploy.yml`, `Dockerfile`, `README.md`).

**Риск:** `-v testtask-uploads:/app/public/uploads` монтирует **всю** папку `uploads/`,
включая `seed/` (демо-скриншоты и PDF, закоммиченные в репозиторий). Если в будущем
образе появятся новые/изменённые файлы в `public/uploads/seed/*`, они точно так же не
попадут в volume — по той же механике.

**Что сделать:** развести монтирование так, чтобы `seed/` всегда бралась из образа
(read-only, не должна быть в volume вообще), а persist нужен только для того, что
приложение пишет само в рантайме:

```yaml
-v testtask-uploads-submissions:/app/public/uploads/submissions
-v testtask-uploads-admin:/app/public/uploads/admin
```

Проверено: приложение пишет ровно в эти два подкаталога
(`src/lib/storage.ts` + `src/app/api/public/upload/route.ts` → `submissions/<id>`,
`src/app/api/admin/upload/route.ts` → `admin`), `seed/` только читается — пути в фиксе
корректны.

**Важно — миграция данных:** при переходе со старого `testtask-uploads` на два новых
volume уже загруженные кандидатами файлы **не переедут автоматически**. Перед сменой
монтирования нужно один раз перекопировать содержимое старого volume в новые
(`submissions/` и `admin/`), иначе существующие сабмишены потеряют вложения.

### 2. ✅ Environment `env_prod` не ограничен по веткам — исправлено

**Что произошло:** секреты (`ADMIN_PASSWORD`, `ADMIN_SECRET`, `NEXT_PUBLIC_BASE_URL`)
лежат в GitHub Environment `env_prod`. Job в `deploy.yml` изначально не был привязан к
этому environment (`environment: env_prod` отсутствовал) — секреты резолвились в пустые
строки, из-за чего логин в админку всегда падал с «Неверный пароль» независимо от
введённого значения. Пофикшено добавлением `environment: env_prod` в job.

**Риск:** в настройках environment сейчас `Deployment branches and tags: No restriction`.
Это значит, что `workflow_dispatch` на **любой** ветке репозитория получает доступ к
прод-секретам, а не только `main`. Хуже: runner — `self-hosted` (см. `deploy.yml`).
То есть тот, кто может создать ветку и запустить workflow, может подменить сам workflow-файл
и не просто прочитать секреты, а **исполнить произвольный код прямо на прод-хосте** и
выкачать секреты наружу. Это фактически RCE на сервере, а не только утечка паролей —
поэтому пункт держим в критичных.

**Что сделано:** через `gh api` для `env_prod` установлен
`deployment_branch_policy: { custom_branch_policies: true }` с единственным правилом
`main` — деплой с любой другой ветки теперь отклоняется на уровне GitHub, до запуска
job на runner'е.

**Не сделано (ограничение биллинг-плана):** `Required reviewers` для этого environment
GitHub вернул `422 Failed to create the environment protection rule — please ensure the
billing plan supports the required reviewers protection rule`. Приватным репозиториям на
текущем плане эта защита недоступна. Если апгрейд плана не рассматривается, ручное
подтверждение перед прод-деплоем компенсировать нечем — при уходе нескольких людей на
`main` стоит вернуться к этому вопросу.

### 3. ✅ Деплой не проверяет, что секреты реально пришли — исправлено

**Что произошло:** ровно из-за пункта 2 деплой «успешно» прошёл (health check зелёный),
хотя `ADMIN_PASSWORD`/`ADMIN_SECRET` были пустыми — единственный симптом обнаружился
только когда попытались залогиниться. Диагностика заняла отдельную сессию.

**Что сделать:** добавить в `Run new container` (или отдельным шагом перед ним) явную
проверку:

```yaml
- name: Verify required secrets are present
  run: |
    test -n "${{ secrets.ADMIN_PASSWORD }}" || { echo "::error::ADMIN_PASSWORD is empty — check env_prod secrets"; exit 1; }
    test -n "${{ secrets.ADMIN_SECRET }}" || { echo "::error::ADMIN_SECRET is empty — check env_prod secrets"; exit 1; }
```

### 6. ✅ Нет бэкапа SQLite-базы — исправлено

Данные живут только в одном docker named volume на одном VPS. Для демо-периода это
осознанно ок (можно `migrate reset`), но как только пойдут реальные ответы кандидатов —
один случайный `docker volume rm`, падение диска или ошибка в скрипте — и всё потеряно
без возможности восстановить.

**Что сделать:** минимум — cron на хосте, копирующий `prisma/data/dev.db` (лучше через
`sqlite3 dev.db ".backup backup.db"`, чтобы не словить partial write) за пределы сервера
(S3/другой хост) на регулярной основе.

## 🟡 Стоит рассмотреть

### 7. ⚠️ In-memory rate-limit — актуально; static-serving 404 — подтверждено и частично исправлено

Уже задокументировано в коде (`src/lib/rateLimit.ts`) — rate-limit держит бакеты в
`Map` в памяти процесса, это подтверждено кодом и переживёт только один инстанс. Если
появится несколько инстансов за балансировщиком, нужен внешний store (Redis и т.п.) —
без изменений, актуально.

**Обновление (2026-07-16) — залипший 404 подтверждён и воспроизведён напрямую:** админ
загрузил файл-вложение к заданию через `/api/admin/upload`, файл физически появился на
диске (`ls -la` показал корректный размер), но прямой запрос к самому процессу Next.js
(`node -e "require('http').get(...)"`, в обход Caddy) вернул `404`. Причина — `next
start` ненадёжно отдаёт файлы, записанные в `public/` уже после старта процесса; он
рассчитан на то, что `public/` статичен и известен на момент сборки. Это не кэш
конкретной страницы (как предполагалось раньше), а особенность раздачи статики.

**Что сделано:** admin-загрузки переведены с публичной статики (`public/uploads/admin/`)
на паттерн, аналогичный файлам кандидатов (п.11) — пишутся в непубличный
`uploads/admin/` и отдаются через `src/app/api/files/admin/[filename]/route.ts`,
читающий с диска на каждый запрос (без авторизации — эти файлы и раньше были
публичными). Подтверждено воспроизведением: загрузка → немедленное скачивание без
рестарта сервера → 200. Покрыто тестом `tests/adminFiles.test.ts`.

**Не закрыто:** это тот же класс бага, что и rate-limit/Map-состояние — специфично для
`public/`-раздачи в Next.js, не общая проблема состояния процесса. Других мест, кроме
`public/uploads/seed/` (build-time, не рантайм-запись — безопасно), под `public/` больше
не осталось.

### 8. ✅ У токена submission нет срока действия — исправлено

Ссылка `/t/<token>` работала бессрочно. Если кандидат перешлёт её кому-то ещё после
дедлайна, доступ не был ограничен.

**Что сделано:** добавлено поле `expiresAt` на `Submission` (миграция
`20260716112233_add_expires_at`). Админский эндпоинт создания submission
(`/api/admin/templates/[id]/submissions`) теперь проставляет `expiresAt = createdAt + 30
дней` (константа `DEFAULT_EXPIRY_DAYS`, без настраиваемого UI — минимальная реализация
по духу пункта). `src/app/t/[token]/page.tsx` показывает отдельный экран «Ссылка
истекла» для непросроченных-но-`expired` submission (уже отправленные — по-прежнему
показывают страницу подтверждения, дедлайн их не блокирует). Проверка задублирована
на бэкенде — `answers`, `upload`, `submit` роуты тоже отклоняют запросы по истёкшей
ссылке (403), чтобы дедлайн нельзя было обойти прямым запросом мимо UI. Покрыто тестами
(`tests/expiry.test.ts`).

### 9. ⚠️ Токен кандидата попадает в access-логи Caddy на сервере — конфиг готов, применить вручную

`Referrer-Policy: no-referrer` (и `X-Robots-Tag`) защищают от утечки токена *наружу* —
через заголовок Referer в чужие сервисы и от индексации поисковиками. Но сам токен
всё равно пишется в access-логи Caddy на сервере в чистом виде (это, по сути, bearer
credential кандидата).

**Не может быть закрыто этой сессией:** `Caddyfile` живёт только на сервере
(`/etc/caddy/Caddyfile`), не в этом репозитории, а SSH-доступа к серверу у меня нет.

**Что сделать (вручную, на сервере):** добавить `log_skip /t/*` в блок сайта — это
штатная Caddy-директива, полностью исключающая совпавшие запросы из access-лога (не
просто обрезает query, а не пишет строку вообще):

```caddyfile
task.uxteam.space {
    reverse_proxy localhost:3000
    header {
        Referrer-Policy "no-referrer"
        X-Robots-Tag "noindex, nofollow"
    }
    log_skip /t/*
}
```

Применить: отредактировать `/etc/caddy/Caddyfile`, затем `sudo systemctl reload caddy`
(или `caddy reload --config /etc/caddy/Caddyfile`, если раннер не под systemd).

### 10. Общий пароль на всю админку, без аудита действий

Пока админ один — не проблема. Если админов станет больше, у системы нет способа
понять, кто именно создал/удалил конкретный `Submission` — единственная identity
сейчас — это один shared secret на всех. Стоит завести хотя бы простой лог действий,
если появится больше одного администратора.

Дополнительно: значение session-cookie — детерминированный `sha256(password:secret)`
(`src/lib/auth.ts`, `src/app/api/admin/login/route.ts`). Оно одинаково для всех сессий,
не ротируется и не отзывается по отдельности — «разлогинить» скомпрометированную сессию
можно только сменив `ADMIN_PASSWORD`/`ADMIN_SECRET` глобально. (В плюс: сама cookie
выставлена корректно — `httpOnly`, `sameSite=lax`, `secure` на https, так что базовый
CSRF на админских мутациях закрыт.) При переходе на несколько админов это надо заменить
на нормальные сессии с уникальным идентификатором.

### 11. ✅ Загруженные файлы кандидатов отдаются публично, без авторизации — исправлено

Middleware (`src/proxy.ts`, matcher `["/admin/:path*", "/api/admin/:path*", "/t/:path*"]`)
защищает только админку и страницу токена. Сами файлы лежат по
`/uploads/submissions/<id>/<uuid>.<ext>` и отдаются статикой Next.js **без всякой
проверки** — то есть ответы кандидатов (скриншоты, PDF) доступны любому, у кого есть URL.
Защита держится только на неугадываемости `randomUUID()` в имени — это ровно та же
«bearer»-модель, что и токен из пункта 9, и такой URL точно так же утекает в access-логи
и историю браузера.

**Что сделать:** отдавать файлы кандидатов через авторизованный route-handler
(проверять admin-сессию или валидность токена сабмишена), а не как публичную статику;
как минимум — не хранить их под `public/` и не логировать полный path.

## План фикса (порядок исполнения)

Приоритет по формуле «риск × дешевизна». Волна 1 — до первого реального потока
кандидатов, волна 2 — до накопления реальных данных, волна 3 — по мере роста.

### Волна 1 — блокеры прод-потока (пункты 2, 3, 5, 1)

1. **п.2 — ограничить `env_prod`** (5 мин, только GitHub UI, риск наивысший):
   `Selected branches → main` + `Required reviewers`. Код не трогаем.
2. **п.3 — verify-secrets шаг** в `deploy.yml` перед `Run new container`
   (проверка `test -n` для `ADMIN_PASSWORD`/`ADMIN_SECRET`). ~10 строк YAML.
3. **п.5 — удалить `diagnose.yml`** (1 файл, снимает поверхность атаки сразу).
4. **п.1 — развести uploads-volume** в `deploy.yml`/`Dockerfile`/`README`:
   два named-volume на `submissions/` и `admin/`. **Обязательно** сначала
   разовая миграция файлов из старого `testtask-uploads`, потом смена монтирования.
   Проверить деплоем, что старые вложения на месте.

### Волна 2 — устойчивость данных и CI (пункты 4, 6, 11)

5. **п.4 — `ci.yml`** на `pull_request`/`push`:
   `npm ci && npx prisma generate && npx tsc --noEmit && npm test`. Зелёный gate до п.11.
6. **п.6 — бэкап SQLite**: cron на хосте с `sqlite3 dev.db ".backup"` + выгрузка
