# Технический долг и план по стабильности/безопасности

Документ собран по итогам первого реального деплоя (ветка `chore/server-recon-extra`,
сервер `task.uxteam.space`) — все пункты основаны на конкретных инцидентах и находках
этой сессии, а не на общих best practices. У каждого пункта — что произошло/почему это
важно и что сделать.

Статус на момент написания: сервис задеплоен, админка и кандидатский флоу (`/t/<token>`)
рабочие, тесты (`npm test`) зелёные, `tsc --noEmit` чистый.

## 🔴 Критично — сделать до реального потока кандидатов

### 1. `testtask-uploads` volume перекрывает `public/uploads/seed/` так же, как раньше `prisma/`

**Что произошло:** volume `testtask-db:/app/prisma` при первом деплое «заморозил» в себе
содержимое `prisma/` (включая `migrations/`) на момент первого запуска. Все последующие
образы с новыми файлами миграций эти файлы просто не видели — `prisma migrate deploy`
молча не находил новых миграций, схема БД разъехалась с кодом
(`P2022: The column main.Submission.openedAt does not exist`). Пофикшено в этой сессии:
volume теперь смонтирован только на `/app/prisma/data`, `migrations/` всегда берётся из
образа (см. `.github/workflows/deploy.yml`, `Dockerfile`, `README.md`).

**Риск:** `-v testtask-uploads:/app/public/uploads` монтирует **всю** папку `uploads/`,
включая `seed/` (демо-скриншоты и PDF, закоммиченные в репозиторий). Если в будущем
образе появятся новые/изменённые файлы в `public/uploads/seed/*`, они точно так же не
попадут в volume — по той же механике.

**Что сделать:** развести монтирование так, чтобы `seed/` всегда бралась из образа
(read-only, не должна быть в volume вообще), а persist нужен только для того, что
приложение пишет само в рантайме:

```yaml
-v testtask-uploads-submissions:/app/public/uploads/submissions
-v testtask-uploads-admin:/app/public/uploads/admin
```

### 2. Environment `env_prod` не ограничен по веткам

**Что произошло:** секреты (`ADMIN_PASSWORD`, `ADMIN_SECRET`, `NEXT_PUBLIC_BASE_URL`)
лежат в GitHub Environment `env_prod`. Job в `deploy.yml` изначально не был привязан к
этому environment (`environment: env_prod` отсутствовал) — секреты резолвились в пустые
строки, из-за чего логин в админку всегда падал с «Неверный пароль» независимо от
введённого значения. Пофикшено добавлением `environment: env_prod` в job.

**Риск:** в настройках environment сейчас `Deployment branches and tags: No restriction`.
Это значит, что `workflow_dispatch` на **любой** ветке репозитория получает доступ к
прод-секретам, а не только `main`.

**Что сделать:** в `Settings → Environments → env_prod → Deployment branches and tags`
поставить `Selected branches` → только `main` (или добавить правило-паттерн для
release-веток, если появятся).

### 3. Деплой не проверяет, что секреты реально пришли

**Что произошло:** ровно из-за пункта 2 деплой «успешно» прошёл (health check зелёный),
хотя `ADMIN_PASSWORD`/`ADMIN_SECRET` были пустыми — единственный симптом обнаружился
только когда попытались залогиниться. Диагностика заняла отдельную сессию.

**Что сделать:** добавить в `Run new container` (или отдельным шагом перед ним) явную
проверку:

```yaml
- name: Verify required secrets are present
  run: |
    test -n "${{ secrets.ADMIN_PASSWORD }}" || { echo "::error::ADMIN_PASSWORD is empty — check env_prod secrets"; exit 1; }
    test -n "${{ secrets.ADMIN_SECRET }}" || { echo "::error::ADMIN_SECRET is empty — check env_prod secrets"; exit 1; }
```

## 🟠 Важно

### 4. Нет CI, гоняющего тесты и типчек автоматически

Сейчас `npm test` и `npx tsc --noEmit` запускались только руками в этой сессии.
Характеризационные тесты (`tests/characterization.test.ts`, `tests/openedAt.test.ts`,
`tests/proxyHeaders.test.ts`, `tests/token.test.ts`) были написаны специально как
ловушка регрессий — но без CI их можно сломать и не заметить до продакшна.

**Что сделать:** добавить `.github/workflows/ci.yml` на `pull_request`/`push`:
`npm ci && npx prisma generate && npx tsc --noEmit && npm test`.

### 5. `diagnose.yml` пора удалить

Разведка сервера выполнена и была одноразовой по изначальному ТЗ. Workflow остаётся в
репозитории и раскрывает в логах прогонов содержимое nginx/caddy конфигов, sudo-статус,
открытые порты — лишняя поверхность, если кто-то получит доступ на запуск workflow или на
логи прошлых прогонов.

**Что сделать:** удалить `.github/workflows/diagnose.yml` (или хотя бы урезать до
безобидного набора проверок, если пригодится ещё раз).

### 6. Нет бэкапа SQLite-базы

Данные живут только в одном docker named volume на одном VPS. Для демо-периода это
осознанно ок (можно `migrate reset`), но как только пойдут реальные ответы кандидатов —
один случайный `docker volume rm`, падение диска или ошибка в скрипте — и всё потеряно
без возможности восстановить.

**Что сделать:** минимум — cron на хосте, копирующий `prisma/data/dev.db` (лучше через
`sqlite3 dev.db ".backup backup.db"`, чтобы не словить partial write) за пределы сервера
(S3/другой хост) на регулярной основе.

## 🟡 Стоит рассмотреть

### 7. In-memory rate-limit и Next.js route-cache не переживают рестарт/несколько инстансов

Уже задокументировано в коде (`src/lib/rateLimit.ts`). Отдельно всплыло в этой сессии:
Next.js закэшировал `404`-страницу в памяти процесса для URL, который на момент первого
запроса ещё не существовал на диске (файл дозаписывался/приложение падало из-за
несовпадения схемы), и продолжал отдавать эту заглушку даже после того, как файл
появился и всё починилось — помог только `docker restart`. Если в будущем появится
несколько инстансов за балансировщиком, ни rate-limit, ни этот кэш не будут
консистентны между ними — тогда точно нужен внешний store (Redis и т.п.).

### 8. У токена submission нет срока действия

Ссылка `/t/<token>` работает бессрочно. Если кандидат перешлёт её кому-то ещё после
дедлайна, доступ не ограничен. Можно добавить `expiresAt` на `Submission` и проверку в
`src/app/t/[token]/page.tsx`.

### 9. Токен кандидата попадает в access-логи Caddy на сервере

`Referrer-Policy: no-referrer` (и `X-Robots-Tag`) защищают от утечки токена *наружу* —
через заголовок Referer в чужие сервисы и от индексации поисковиками. Но сам токен
всё равно пишется в access-логи Caddy на сервере в чистом виде (это, по сути, bearer
credential кандидата). Стоит либо не логировать полный path/query для `/t/*`, либо
явно ограничить retention этих логов.

### 10. Общий пароль на всю админку, без аудита действий

Пока админ один — не проблема. Если админов станет больше, у системы нет способа
понять, кто именно создал/удалил конкретный `Submission` — единственная identity
сейчас — это один shared secret на всех. Стоит завести хотя бы простой лог действий,
если появится больше одного администратора.
