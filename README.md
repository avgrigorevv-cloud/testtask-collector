# Конструктор тестовых заданий

Сервис для сбора откликов на тестовые задания с кастомизируемым флоу под каждую роль
(стажёры-разработчики, исследователи, дизайнеры и т.д.).

## Как это устроено

- **Шаблон** — админ собирает флоу из блоков в конструкторе (`/admin`).
- **Блоки**: прикреплённый файл-инструкция, ссылка, текстовый ответ, загрузка файла,
  разметка скриншотов (кандидат кликает по картинке и оставляет комментарий к точке).
- **Прохождение** — для каждого кандидата админ создаёт персональную ссылку `/t/<token>`,
  по которой кандидат проходит флоу без регистрации.
- Admin-часть закрыта простой авторизацией по паролю (см. `ADMIN_PASSWORD` ниже) — без
  многопользовательской системы, этого достаточно для MVP.

В сиде (`prisma/seed.ts`) уже есть три примера шаблона: бэкенд-стажёр (с приложенным PDF
тестового задания и полем под ссылку на git-репозиторий), UX-исследователь (три скриншота
главной sogaz.ru для разметки проблем юзабилити) и дизайнер (загрузка портфолио + ссылка).

## Стек

Next.js 16 (App Router) · TypeScript · Tailwind CSS · Prisma 7 + SQLite (better-sqlite3 driver
adapter) · локальное хранилище файлов в `public/uploads`.

## Запуск

```bash
npm install
cp .env.example .env      # при желании поменяйте ADMIN_PASSWORD
npx prisma migrate dev    # создаёт SQLite-базу prisma/dev.db
npx prisma db seed        # заполняет тремя примерами шаблонов
npm run dev
```

Открыть [http://localhost:3000/admin](http://localhost:3000/admin) и войти паролем из
`ADMIN_PASSWORD` (по умолчанию `changeme123`).

Ссылки на кандидатские прохождения печатаются в консоль после сида, либо их можно получить
в админке: шаблон → «Прохождения» → «Копировать ссылку».

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | путь к SQLite-файлу, например `file:./prisma/data/dev.db` — **должен указывать под `prisma/data/`**, потому что именно туда смонтирован volume `testtask-db` (см. ниже); значение резолвится относительно `process.cwd()` (в контейнере — `/app`), а не относительно `schema.prisma`, так как `@prisma/adapter-better-sqlite3` просто отрезает префикс `file:` и передаёт остаток в `better-sqlite3` как есть |
| `ADMIN_PASSWORD` | пароль для входа в `/admin` |
| `ADMIN_SECRET` | соль для подписи сессионной cookie админа |
| `NEXT_PUBLIC_BASE_URL` | базовый URL для кнопки «Копировать ссылку» в админке |

## Деплой

Важно: приложение хранит данные в локальном SQLite-файле (`prisma/data/dev.db`) и в локальной
файловой системе (`public/uploads`). Это значит, что хостинг должен давать **постоянный
диск**, который не сбрасывается между деплоями/перезапусками — обычный serverless-хостинг
(Vercel, Netlify Functions и т.п.) для этого не подходит: файлы и база будут теряться.
Подходят Railway, Render, Fly.io, VPS с Docker/PM2 — любой хостинг с постоянным контейнером
и volume.

В репозитории есть `Dockerfile`. Сборка образа не проверялась локально (в этом окружении
не было доступного Docker), проверьте `docker build` перед продакшн-использованием.

```bash
docker build -t testtask-collector .
docker run -d \
  -p 3000:3000 \
  -e ADMIN_PASSWORD=... \
  -e ADMIN_SECRET=... \
  -e NEXT_PUBLIC_BASE_URL=https://your-domain.example \
  -e DATABASE_URL=file:./prisma/data/dev.db \
  -v testtask-db:/app/prisma/data \
  -v testtask-uploads-submissions:/app/uploads/submissions \
  -v testtask-uploads-admin:/app/uploads/admin \
  -v testtask-uploads-captures:/app/uploads/captures \
  testtask-collector
```

Volume монтируется на `/app/prisma/data` (не на весь `/app/prisma`!), чтобы файл `dev.db`
сохранялся между перезапусками контейнера, а `migrations/` каждый раз бралась свежая из
образа — иначе новые миграции из будущих деплоев будут перекрыты тем, что volume
«заморозил» при первом запуске. По той же причине два runtime-write каталога монтируются
по отдельности, а не общий `public/uploads`: `testtask-uploads-submissions` →
`/app/uploads/submissions` и `testtask-uploads-admin` → `/app/uploads/admin`. Оба каталога
специально **не под** `public/` — `next start` ненадёжно отдаёт файлы, записанные в
`public/` уже после старта процесса (подтверждено на проде, см. `TECH_DEBT.md` пункт 7),
поэтому оба вида загрузок отдаются через route-handlers
(`src/app/api/files/submissions/[id]/[filename]/route.ts` — с проверкой токена/admin-сессии,
`src/app/api/files/admin/[filename]/route.ts` — без авторизации, как и раньше), а не как
статика. `public/uploads/seed/` (демо-скриншоты и PDF) volume не монтируется вообще и всегда
берётся из образа — это read-only-данные, в рантайме туда ничего не пишется. При первом
запуске контейнер сам применяет миграции (`prisma migrate deploy`) — сид (`prisma db seed`)
нужно прогнать один раз вручную (`docker exec <container> npx prisma db seed`), если нужны
примеры шаблонов.

**Разовая миграция (2026-07-16):** `testtask-uploads-admin` ранее монтировался на
`/app/public/uploads/admin`, теперь — на `/app/uploads/admin`. Volume тот же (данные внутри
не теряются — Docker volume идентифицируется по имени, не по точке монтирования), поэтому
никаких ручных действий не требуется — после деплоя этой версии просто проверьте, что
admin-файлы (вложения к заданиям) открываются.

Если в будущем понадобится serverless-хостинг (Vercel и т.п.), архитектуру нужно будет
поменять: SQLite → Postgres (например, через `@prisma/adapter-pg`), а `public/uploads` →
объектное хранилище (S3-совместимое).

## Бэкапы БД

Данные живут в единственном docker volume (`testtask-db`) на одном VPS — без регулярного
бэкапа `docker volume rm`, падение диска или неудачная миграция теряют всё без возможности
восстановления. `scripts/backup-db.sh` делает согласованный снепшот через SQLite-команду
`.backup` (не сырое копирование файла — избегает partial write на живой базе) внутри
короткоживущего контейнера, который монтирует `testtask-db` volume только для чтения,
сжимает результат gzip'ом и складывает в `BACKUP_DIR` с именем вида
`dev-YYYYMMDD-HHMMSS.db.gz`, удаляя бэкапы старше `RETENTION_DAYS` дней. Скрипт завершается
ненулевым кодом при любой ошибке — рассчитан на запуск из cron с проверкой кода возврата.

**Проверить вручную один раз:**

```bash
chmod +x scripts/backup-db.sh   # если бит исполняемости не сохранился при клонировании
./scripts/backup-db.sh
# либо явно:
BACKUP_DIR=/var/backups/testtask-collector RETENTION_DAYS=14 ./scripts/backup-db.sh
```

Убедитесь, что в `BACKUP_DIR` появился файл `dev-<timestamp>.db.gz` и что его можно
распаковать и открыть sqlite3 (`gunzip -k <файл> && sqlite3 <файл без .gz> ".tables"`).

**Поставить в cron на VPS** (например, ежедневно в 03:00, вывод — в лог-файл для алертинга
по коду возврата/содержимому лога):

```cron
# crontab -e
0 3 * * * BACKUP_DIR=/var/backups/testtask-collector RETENTION_DAYS=14 /path/to/testtask-collector/scripts/backup-db.sh >> /var/log/testtask-backup.log 2>&1
```

**Вынести бэкапы за пределы сервера.** Локальный бэкап на том же VPS не защищает от отказа
самого VPS (диск, провайдер, компрометация хоста) — цель «за пределы сервера»
(TECH_DEBT.md, п.6) этим одним скриптом не закрывается, это отдельный шаг. У проекта пока
нет настроенного S3-бакета или второго хоста, поэтому здесь не прописаны конкретные
credentials — вместо этого опишем форму решения, которую нужно донастроить вручную один раз
тому, кто разворачивает бэкапы:

- добавить в cron ещё один шаг после `backup-db.sh`, который синхронизирует `BACKUP_DIR` на
  внешнее хранилище — например `rclone sync "$BACKUP_DIR" remote:testtask-backups` (S3-совместимое
  хранилище, `remote` настраивается один раз через `rclone config`), либо `rsync`/`scp` на
  второй хост:
  ```cron
  5 3 * * * rclone sync /var/backups/testtask-collector "${BACKUP_REMOTE:?set me}" >> /var/log/testtask-backup-sync.log 2>&1
  ```
- `BACKUP_REMOTE` (или аналогичная переменная) должен быть заполнен реальным значением тем,
  кто настраивает сервер — это ручной one-time setup (создать бакет/хост, положить
  креды/rclone-конфиг), не то, что скрипт должен знать или хардкодить.

**На будущее** — если сервис станет бизнес-критичным, стоит рассмотреть
[litestream](https://litestream.io/) для непрерывной репликации SQLite в S3-совместимое
хранилище вместо периодических снепшотов (TECH_DEBT.md, п.6); здесь это не внедряется,
только отметка на будущее.

## Безопасность

- **Загрузка файлов** (админ и кандидат) валидируется на сервере по allowlist расширений
  (документы, изображения, видео, архивы — см. `src/lib/storage.ts`) и ограничена 25 МБ на
  файл. Типы, которые браузер мог бы исполнить как активный контент при прямом открытии
  (`.html`, `.svg`, `.js` и т.п.), отклоняются, независимо от того, что указано в `accept`
  на клиенте — тот атрибут это лишь подсказка браузеру, не защита.
- **Ссылки** — ответы типа «ссылка» валидируются на сервере (только `http`/`https`,
  см. `src/lib/url.ts`) и повторно проверяются перед рендером в просмотре ответа у
  админа — так кандидат не может подсунуть `javascript:`-ссылку, которая выполнится в
  браузере админа при клике.
- **Ответы кандидата** проверяются на принадлежность реально существующему блоку шаблона
  (`blockId` + `type` сверяются со схемой шаблона), значение ограничено по размеру
  (200 КБ) — не даёт создавать произвольные записи или раздувать базу.
- **Админка** закрыта паролем (`ADMIN_PASSWORD`), сравнение пароля и сессионного токена —
  константное по времени (`timingSafeEqual`), не подвержено тайминг-атаке. `/api/admin/login`
  ограничен 10 попытками за 5 минут на IP. Cookie сессии — `httpOnly`, `sameSite=lax`,
  `secure` в проде.
- Загрузка кандидатом (`/api/public/upload`) и сохранение ответов
  (`/api/public/submissions/:token/answers`) ограничены по частоте на токен, чтобы
  токеном нельзя было засыпать диск/базу запросами.
- Rate-limiting — в памяти процесса (см. `src/lib/rateLimit.ts`), рассчитан на единственный
  постоянный процесс (см. «Деплой» выше); за балансировщиком из нескольких инстансов
  понадобится общее хранилище (Redis и т.п.).
- Не проверялось: устойчивость к нагрузочным/фаззинг-атакам, полноценный антивирус-скан
  загружаемых файлов (только проверка расширения) — для более чувствительного использования
  стоит добавить сканирование содержимого перед продакшеном.

## Расширение для браузера: скриншоты с метками

В папке `extension/` лежит расширение для Chrome. Оно делает скриншот видимой части любой
страницы, дает поставить метки и области с комментариями, измерить отступы между элементами
и скопировать результат в буфер обмена. **Расширению сервер не нужен**: все работает
локально. Серверная часть ниже нужна только для необязательного сохранения скриншотов по
логинам и датам (`uploads/captures/<userId>/<ГГГГ-ММ-ДД>/`).
Публикация в Chrome Web Store: `extension/STORE.md`, политика конфиденциальности: `PRIVACY.md`.

- **Логины.** Админ создает их в `/admin/captures`. У каждого логина своя папка: файлы
  лежат в `uploads/captures/<userId>/`, записи в таблице `Capture`.
- **Авторизация расширения.** `POST /api/ext/login` выдает Bearer-токен на 30 дней, в базе
  хранится только его sha256. Смена пароля в админке отзывает все токены этого логина.
- **Прием.** `POST /api/ext/captures`: оригинальный PNG, PNG с нарисованными метками,
  метки, адрес и заголовок страницы.
- **Отдача файлов.** `GET /api/files/captures/<id>` доступен админу и владельцу скриншота,
  остальным 404. `?variant=annotated` отдает версию с метками, `?download=1` скачивает.
- **Деплой.** Нужен отдельный volume `testtask-uploads-captures` → `/app/uploads/captures`
  (уже добавлен в `deploy.yml`).

Установка и использование расширения описаны в `extension/README.md`.

## Структура

- `src/app/admin` — админка (конструктор шаблонов, список прохождений, просмотр ответа).
- `src/app/t/[token]` — публичный флоу кандидата.
- `src/app/api/admin/*` — защищённые ручки для админки.
- `src/app/api/public/*` — публичные ручки для кандидата (ответы, файлы, отправка).
- `src/lib/blocks.ts` — типы блоков и их конфигурации.
- `src/components/shared/ImageAnnotate.tsx` — общий компонент разметки скриншотов
  (используется и в кандидатском флоу, и в просмотре ответа админом).
- `src/app/api/ext/*` — ручки браузерного расширения (вход, прием скриншотов).
- `src/app/admin/(dashboard)/captures` — папки скриншотов по логинам.
- `extension/` — само расширение (Manifest V3).
